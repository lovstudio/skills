# 命名判断

名称负责识别，简介负责边界。不能为了短，把专注于仓库简介的能力包装成无所不能
的 GitHub 工具；也无需把每个输入格式和次要功能都写进名称。

| 维度 | 判断方式 | 常见误区 |
| --- | --- | --- |
| 准确 | 名称、简介、实际输入输出一致 | 用“仓库信息”模糊“优化仓库简介”的任务 |
| 简短 | 去掉无助识别的词，读一遍能复述 | 堆砌格式、实现步骤和限制 |
| 优雅 | 自然节奏或意象，符合受众 | 生硬翻译、缩写拼接、形容词堆叠 |
| 一致 | 同组语气协调，子能力清楚区分 | 同一后缀或强制“对象＋动作” |

四项是编辑标准，不能凭空量化。先排除能力误导、重名与认可值冲突，再比较候选。

## 表达方式

- 功能：GitHub 仓库简介优化。具体任务无需套用“大师”。
- 结果：专业海报、专业信息图。直接指向用户得到的制品。
- 角色：BP 大师、写书专家、官网小能手。角色感应符合交付能力。
- 意象：汉字镜、人人字幕。简介补足操作范围，名称保留记忆点。

这些是历史用户认可的表达方式，不据此给不相关 Skill 硬套名字。
“专业”出现在已认可产品专名中，与正文无依据自夸不是一回事。

## 认可值精度

保留原字、空格、大小写和作用对象：`PDF大师` 不擅自加空格，`万能微信秘钥`
不擅自改字，`BP 大师` 对应 deck 能力，中文认可不代表英文也已获认可。
当前用户明确改名时记录新基准，不能把旧基准锁成不可改变的规则。

完整基准见 [案例来源](../cases/evidence/provenance.md)。它们只用于本包历史案例；
为其他用户起名时，从其 brief 与 Profile 读取偏好。

## 缩短与去前缀

作者或工作室前缀放在署名中。GitHub、微信、PDF 等若帮助识别任务目标或产物，
应保留。优先删去缺乏具体贡献的“智能、全能、一站式、解决方案”等修饰。
大师、专家、神器、小能手、人人没有固定黑名单，逐项判断是否自然、是否误导。
长度偏好是软约束，已认可名称与必要识别信息优先。

## 中英文与整组

英文自然表达同一核心能力；意象不必逐字翻译，也不能把子能力译成完整套件。
查完全重名后，人工检查近义、近音冲突与系列关系。同组可有不同语法：
“BP 工坊、BP 蓝图、BP 大师、BP 精修”分别对应入口、提纲、演示稿与润色。
不要虚构功能差异来解决真实重叠；产品合并与架构判断留给相应任务。
