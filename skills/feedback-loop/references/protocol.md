# 反馈飞轮协议 v1

本文件是反馈飞轮的单一真源：信号如何识别、分级、记录、归因、闭环与统计。
模块入口只负责执行，判定口径冲突时以本文件为准。

## 1. 两条通道

| 通道 | 定义 | 典型输入 |
| --- | --- | --- |
| `explicit` | 用户主动 judge | 表情、短语、评分、明确指令 |
| `passive` | 从语气、行为与节奏推断 | 反复纠偏、无奈反问、敷衍、明显冷场 |

被动信号必须带用户原话作为证据，`confidence` 永远小于 1；
没有原话证据的推测不落账。沉默本身不是证据，只在与上一次互动形成对照时才算线索。

## 2. 极性与强度

极性取值：`positive`、`negative`、`mixed`、`neutral`。

| 强度 | 含义 | 例子 |
| --- | --- | --- |
| 1 | 轻微倾向 | “还行”“可以先这样” |
| 2 | 明确偏好但不强烈 | “这样是对的”“有点不对” |
| 3 | 明确满意或不满 | “很好”“不对，重来” |
| 4 | 强烈表态 | “做得很棒”“太差了” |
| 5 | 极端或重复情绪 | “就是这个，太好了”“怎么又错了” |

落账门槛：强度大于等于 3 直接落账；强度 1–2 只有在同一会话重复 2 次、
或 7 天内同类出现 3 次时才作为 pattern 事件落账。

### 判定红线

- 没有原话证据的推测不记录。
- 需求变更记为 `direction_change`，不按不满处理。
- 客气或客套的“还行”不升级成强烈信号。
- 一句话同时含正负两面记 `mixed`，不挑一边。
- 把握不足时把 `confidence` 降到 0.4 以下并写明原因；宁可少记，不错记。

## 3. 类型

| kind | 说明 |
| --- | --- |
| `praise` | 明确肯定本轮结果 |
| `delight` | 超出预期的惊喜 |
| `approval` | 认可方案或方向 |
| `lukewarm` | 态度平淡，未达预期但未反对 |
| `dissatisfaction` | 明确不满 |
| `frustration` | 受挫、无奈、反复解释 |
| `anger` | 强烈负面情绪 |
| `correction` | 用户指出具体错误 |
| `repeat_complaint` | 同类问题再次出现 |
| `disengagement` | 冷场、敷衍、明显失去耐心 |
| `direction_change` | 用户改变目标或删减范围 |

## 4. 作用域阶梯

反馈先按最窄层处理，逐级才向上：

1. `task` — 只改当前产物，不动规则。
2. `skill` — 改最窄的 canonical Skill。
3. `reference` — 改该领域的 reference。
4. `root-prompt` — 改跨领域全局原则。

宿主没有 Skill 层时，映射为“产物 → 项目规则 → 宿主指令文件”。
升级条件：用户明确说“以后都这样”，或同类可复用信号在不同任务里出现 2 次以上。
宿主已有反馈分层规则时，编号以宿主为准，层级语义与本阶梯一致。

### 最小改动与验证清单

规则层（skill、reference、root-prompt）改动按此清单执行：

1. 只改与判据直接相关的句子，不顺手重写。
2. 保留原有编号与命名；新增规则追加编号，不重排历史编号。
3. 同步更新版本号与变更记录。
4. 校验引用与路径可解析，被引用的文件真实存在。
5. 规则被复制到其他宿主或工作区时，逐份回读校验和。
6. 在原任务路径上复现，确认问题消失。
7. 完成后回填 `change-applied` 到 `verified`；未完成写 `change-proposed` 并给出复查条件。

## 5. 闭环状态机

```text
captured → triaged → change-proposed → change-applied → verified
                          ↘ declined
                          ↘ deferred（写明复查条件）
```

- 负信号默认在当前轮做最小修复并在原路径回读；无法立即修复时停在
  `change-proposed`，并给出下一步与复查条件。
- `verified` 才算闭环；正信号也要回填结果，说明哪一层被确认有效。
- 状态变化一律以新的 `feedback-outcome/v1` 记录追加，不修改历史事件。

### 账本操作

- 事件与结果都是追加式写入；结果只以新的 `feedback-outcome/v1` 记录表达，历史不改。
- 同会话、同证据、同类型且间隔 10 分钟内视为重复，只保留一条。
- 删除请求以 `declined` 加 `note: tombstone` 表达，历史事件保持不变。
- 写入统一走 `scripts/feedback_store.py`；`verify` 在结构问题存在时返回非零。

## 6. 隐私与安全

- `evidence` 截断到 240 字符，去掉凭据、密钥、密码、私人联系方式与第三方隐私。
- 不整段转录对话；只保留判定所需的最小片段。
- 默认只写本地账本；上传、共享或用于训练必须获得用户显式授权。
- 报告引用原话前先去敏，并允许用户删除事件（删除以 tombstone 记录，不改历史）。

## 7. 统计口径

- 趋势按本地日期分组，同时记录 UTC 时间戳。
- 满意率 = positive 事件 / 全部有效事件；`mixed` 单独列出，不计入分子。
- 未闭环清单 = 状态不在 `verified` 或 `declined` 的事件，按时间从早到晚。
- signal-to-fix 时长 = 事件时间到第一条 `verified` 结果的时间差，取中位数。

## 8. 与规则迭代的关系

本协议只决定“记什么、怎么归因、如何验证”，不改变授权边界：
发布、外发、共享权限与高影响操作仍然遵循用户原有授权；
满意度信号不能作为绕过确认的理由。
