# B 站投稿约束

## 执行优先级

1. 当前账号投稿页展示的限制、校验提示与计数器；
2. 本文记录的实测基线；
3. `scripts/check_video.py --platform bilibili` 的保守默认值。

页面文案与本文不同时，记录原文并以页面为准。

## 视频硬限制

| 项目 | 值 | 证据 |
| --- | --- | --- |
| 文件大小 | ≤ 16 GB；粉丝 ≥1000 的账号 ≤ 64 GB | 上传页原文「视频大小16G以内，时长10小时以内」（2026-08-18、2026-09-27 读取）；64G 为页面对粉丝 ≥1000 账号的说明 |
| 视频时长 | ≤ 10 小时 | 同上 |
| 视频码率 | **无上限** | 同一页面只写大小与时长，没有任何码率要求（2026-09-27 读取） |
| 推荐容器 | MP4 / MOV / MKV（建议项） | 同一页面还推荐 1080P / 4K（2026-09-27 读取） |

比视频号宽得多（4 GiB / 2 小时），所以**不要拿视频号的默认值去卡 B 站**：
一条 491 MB / 18m45s 的横版片在视频号是接近上限的大件，在 B 站是小件。
脚本默认仍按 16 GB 保守拦截；页面对当前账号显示 64G 时，记录原文后用 `--max-gb` 覆盖重跑。

## 码率：没有上限，直接传渲染母版

B 站会对每条投稿重新转码，高码率母版反而是更好的转码源。所以：

- 直接上传 B 站的已批准平台成片（渲染母版），不因码率或体积在上传前重压；
- 视频号的「≤ 10 Mbps」建议，以及视频号长视频把预检 `warnings` 当门槛、先重压再上传的
  做法，都只属于视频号，不搬到 B 站。同一期视频号用了重压版时，B 站仍传母版；
- `check_video.py --platform bilibili` 不报 `video_bitrate_high` / `video_bitrate_unknown`，
  只在 `notes` 里给一条 `video_bitrate_no_platform_cap` 提示；
- 只有 B 站页面真的返回转码失败时，才按 [重压方案](../encoding-recipes.md) 处理。

这条是 2026-09-27 被用户叫停换来的：脚本当时对两个平台都报 `video_bitrate_high`，
agent 据此开始把一条 20 Mbps、2.08 GB、13:47 的母版重压到 9 Mbps。这一步没有平台依据，
还在 B 站自己转码之前多加了一次有损压缩。

容器同理：MP4 / MOV / MKV 都是投稿页推荐的格式，`check_video.py --platform bilibili`
对这三种不报容器警告，其他容器才报 `container_not_recommended`。母版是 MOV 或 MKV 时
直接上传，不要为了换成 MP4 重新封装或转码；「只推荐 MP4」是视频号的口径。

## 文案字数限制

| 字段 | 上限 | 证据等级 |
| --- | --- | --- |
| 稿件标题 | 80 | 页面计数器 `n/80`；**未在 2026-08-18 逐字撞过上限** |
| 简介 | 2000 | 计数器 `n/2000`，实测读到过 |
| 合集标题（创建弹窗） | 20 | `input.maxLength === 20`，实测 |
| 合集标题（编辑表单） | **50** | `input[placeholder="请输入合集标题"].maxLength === 50`，实测 |
| 标签 | 10 个 | 平台上限 |

## 合集：先随便建，再改名成全称

这条是 2026-08-18 被用户退回一次换来的。

创建弹窗限 20 字，《手工川与你一起学 DeepSeek Harness》25 字进不去。当时我据此
换成了系列短名——**错的**。「编辑合集」表单限 50 字，先建一个短名再改名成全称就行
（改完计数器读到 `25/50`）。

判据：**撞到任何字数上限，先分别读创建表单和编辑表单的 `maxLength`，两者不一定相同。**
默认用系列全称，降级用短名必须有实证。系列名的两个形态见
`lov-media-creator/references/series-template.md`「系列名的两个形态」。

改合集名会让合集进「正在审核」，但**稿件归属不受影响**（实测：改名后两期仍在合集里）。

## 标签的话题专用命名空间

部分标签名无法作为自定义标签添加，toast 原文：

```
当前tag为话题专用，不允许自定义添加
```

2026-08-18 实测被拒的名字：`DeepSeekHarness`、`独立开发者`、`插件开发`。
这不是字符集问题，也不是长度问题，是平台把这些名字划给了话题体系。

做法：优先点推荐 chip `.hot-tag-item`（页面上出现的一定能加），撞到拒绝时换同义词，
不要反复重试同一个名字。当时的替代是 `架构设计` / `开源` / `编程` / `教程`。

**`check_copy.py --platform bilibili` 只能挡下已知名单**，新名字仍会在页面上被拒——
所以填标签后要读一次 toast，不能只看请求返回。

## 封面必须交 16:9

B 站有两个独立封面槽，而**列表、空间、信息流用的都是 16:9 槽**。只传 4:3 等于没传
（详见 [投稿页结构](page-anatomy.md)「封面是两个独立的槽」）。

竖版素材做 16:9 的合成方式（2026-08-18 用的那套）：
4:3 原图居中满高放在中间，背景是同一张图放大、模糊、压暗，输出 1920×1080。
这样两侧不是纯色条，也不裁掉标题。

## 稿件可编辑，这一点和视频号相反

视频号发布不可逆；B 站稿件投出去之后仍可 `?type=edit&bvid=` 改标题、简介、标签、封面、合集。
所以：

- `publish` 的终稿确认门禁在 B 站仍然要走（用户批准的是原始文案，不是平台改写后的），
  但**发错了不是不可挽回**，报告里要把这一点说清楚，不要按视频号的口径渲染成灾难；
- 改完任何字段都要重新点「立即投稿」，否则不生效。
