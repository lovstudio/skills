# 提交前发布门禁（跨平台）

## 终稿必须由用户确认（`publish`）

字段表全项 `pass` 只是**可以问了**，不是可以发了。`publish` 在此进入
`awaiting_confirmation`：通知用户、把终稿交给他过目、等到明确同意，才点主提交按钮。

理由不是「不可逆」，而是字段表里有一部分内容用户**从没看见过**——上传后平台会拒掉或改写
文案（视频号短标题超限、禁用符号；B 站标签被话题命名空间拒绝）、自动带入位置、
给出与预期不同的封面槽位数。用户批准的是原始文案，不是这些改写后的结果。

呈现终稿时把改写过的字段单独标出来：

```text
被平台改写：
  short_title  expected 「DeepSeek Harness 发布，我第一时间研究了它的架构设计」(34 字)
               actual   「第一时间读 Harness 架构」(16 字)
               reason   平台报「标题超过16字限制」+「符号仅支持…逗号可用空格代替」
  location     expected 不带 → actual 平台自动带入「上海市」，已清为「不显示位置」
  cover        expected 3:4 + 4:3 → actual 页面只有一个 3:4 槽，4:3 无上传入口
  tags         expected DeepSeekHarness/独立开发者/插件开发
               actual   架构设计/开源/编程/教程
               reason   B 站报「当前tag为话题专用，不允许自定义添加」
```

通知走 `scripts/notify_user.py`（系统通知 + 语音播报），因为用户可能不在终端前；
然后停下等他回话，不设超时、不默认同意。会话早先的「发吧」是启动授权，不是终稿确认。

`draft` / `schedule` / `status` 不需要这一步：草稿可改，定时到点前可撤，`status` 只读。

### 可逆性按平台不同，口径也要跟着变

| 平台 | 发布后可否改 | 报告口径 |
| --- | --- | --- |
| 微信视频号 | **不可逆**。发出去只能删了重发 | 门禁是最后一道闸，出错的代价说清楚 |
| Bilibili | 可编辑。`?type=edit&bvid=` 能改标题、简介、标签、封面、合集 | 门禁照走，但不要把可修复的问题渲染成灾难；同时**改完必须重新点「立即投稿」**，不然不生效 |

两个平台都走终稿确认，区别只在事后。

## 完整字段表

`publish` 在进入 `awaiting_confirmation` 前必须形成并回读下表。`required=true` 的项目
只要有一项不是 `pass`，就停在提交前。一次 `js()` 读完的做法见各平台的 page-anatomy。

### 通用项

| 字段 | 默认要求 | 通过证据 |
| --- | --- | --- |
| 账号 | 必填 | 页面可见账号与预期名称逐字一致 |
| 描述 / 简介 | 必填 | 记录 `source`；编辑区实际文本非空，与该来源的冻结全文逐字一致（读长度，不看外观） |
| 封面 | 页面实际存在的每个槽位都必填 | 槽位数现场实测，逐个上传并验安全区 |
| 定时 | 必填 | 「不定时」或目标定时时间的真实 radio/state 与预期一致 |
| 页面校验错误 | 必须为空 | `[class*=error]` 文本集合为空 |

### 微信视频号专有

| 字段 | 默认要求 | 通过证据 |
| --- | --- | --- |
| 短标题 | 必填 | `value` 非空、**≤16 字、不含逗号**，且没有平台校验警告 |
| 话题 | 至少 1 个 | 平台已识别的独立话题标签（`span.topic` 节点个数） |
| 原创 | 按会话要求 | 原创条款已同意，主复选框 `checked=true` |
| 视频标注 | 按会话要求 | `.select-display` 文本与要求逐字一致 |
| 位置 / 合集 / 评论 / 可见范围 | 按用户要求或平台默认 | 实际值已回读并写入字段表 |

### Bilibili 专有

| 字段 | 默认要求 | 通过证据 |
| --- | --- | --- |
| 稿件标题 | 必填 | `value` 非空、≤80 字 |
| 分区 | 必填 | 已选分区名文本 |
| 标签 | 至少 1 个 | 标签节点个数与文本；**先清掉平台按账号名自动猜的那几个** |
| 类型（自制/转载） | 必填 | 实际选中项 |
| 合集 | 按用户要求 | 精确 `===` 匹配到的合集名 |
| 16:9 封面 | 必填 | 投稿后 `api.bilibili.com/x/web-interface/view?bvid=` 的 `pic` 拉下来看过 |

建议用固定结构记录：

```text
field: short_title
required: true
source: user-provided
expected: AI时代 人靠什么成为自己？
actual: AI时代 人靠什么成为自己？
result: pass
```

描述一旦标记 `source=user-edited`，终稿字段表的 `expected` 就是接手页面时冻结的实际文本，
不是 agent 旧草稿或本地文案文件。封面、合集、原创、位置或话题操作后需再次逐字回读；变化
即 `fail`，不得继续提交。

## 文案预检先离线跑掉

先跑 `scripts/check_copy.py --platform <平台>` 把能离线判定的挡掉，再开浏览器。
纯字符串判定撞一次就多一个「填入 → 失焦 → 读校验 → 改写」的页面往返。

### 视频号（2026-08-17 实测原文）

| 字段 | 限制 | 平台报错原文 |
| --- | --- | --- |
| 短标题 | ≤ **16** 字 | 标题超过16字限制 |
| 短标题 | 禁用**逗号**；只放行书名号、引号、冒号、加号、问号、百分号、摄氏度 | 标题包含特殊字符，符号仅支持书名号、引号、冒号、加号、问号、百分号、摄氏度，逗号可用空格代替 |
| 合集标题 | ≤ **10** 字，且**创建后不可修改** | 创建弹窗计数器 `0/10`；「合集创建后，标题不可修改」 |

**短标题不是标题**。项目文案里那条几十字的推荐标题属于描述首句的量级，直接填短标题必被拒。实测案例：34 字的「DeepSeek Harness 发布，我第一时间研究了它的架构设计」→ 压到 16 字的「Harness 发布，我去读架构」仍因逗号被拒 → 最终「第一时间读 Harness 架构」通过（用空格代停顿）。两轮往返本可以被一次离线预检省掉。

**合集超长时不要截断照建**。视频号的合集名创建后改不了，会跟着整个系列走；停下来重新起一个
≤10 字的短名，或本期先不挂、之后在「内容管理 - 视频 - 合集」补挂。

### Bilibili（2026-08-18 实测）

| 字段 | 限制 | 证据 |
| --- | --- | --- |
| 标题 | ≤ 80 字 | 页面计数器；未逐字撞过上限 |
| 简介 | ≤ 2000 字 | 计数器 `n/2000` |
| 合集（创建弹窗） | ≤ 20 字 | `maxLength === 20` |
| 合集（编辑表单） | ≤ **50** 字 | `maxLength === 50` |
| 标签 | 部分名字属于话题专用命名空间，禁止自定义添加 | toast「当前tag为话题专用，不允许自定义添加」 |

**撞上限先证实，再降级用短名。** B 站的创建弹窗和编辑表单上限不同（20 vs 50），
先建再改名就能用系列全称。2026-08-18 我在这里直接按创建弹窗的 20 字换了短名，被用户退回。
判据：**两个表单各读一次 `maxLength`**，默认用全称。

其余仍然成立：

- 各字段分别校验，不能因为预览卡片出现文案就推断编辑字段已经持久化。
- 视频号把话题解析成独立标签（`span.topic[data-type=topic]`）后才算通过；纯文本 `#` 不会被解析。
- 遇到平台提示时，只做它明确建议的最小修正；失焦后确认提示消失。
- 重发任务继承同一会话最后确认的全文和标签，不从被删除的旧条目反向猜测。

## 封面与安全区

### 先数槽位，再决定传几张

槽位数量是平台前端的当期实现，会变，**不要写死**。

| 平台 | 观测到的槽位 |
| --- | --- |
| 视频号 | 一次读到 1 个（「个人主页和分享卡片(3:4)」，两个预览由同一张 3:4 裁出，4:3 无入口）；另一次读到 2 个（`["个人主页卡片","3:4","分享卡片","4:3"]`）。**同一天两次会话结果不同** |
| Bilibili | 固定 2 个独立槽（首页推荐 4:3 / 个人空间 16:9），但**一次上传只落到当前激活的槽** |

视频号读槽位：

```js
Array.from(sr.querySelectorAll('.cover-tips')).map(e => e.innerText.trim())
```

按读到的条数走。视频号只读到一个槽时，传 3:4 并在报告里说明 4:3 备用件未被使用及原因，
不要去找不存在的第二个入口，也不要因此判定流程走错了。

封面的 `input[type=file]`（`accept` 含 `image/`）**只在封面编辑器打开后才出现**，
关闭时穿透遍历也找不到。先打开编辑器，再定位文件输入。

### B 站的 16:9 必须用接口回读

这是最容易误报成功的一处：表单显示「封面设置」只证明 4:3 有图。列表、空间、信息流用的是 16:9。

```bash
curl -s 'https://api.bilibili.com/x/web-interface/view?bvid=BVxxx' | python3 -c \
  'import json,sys; print(json.load(sys.stdin)["data"]["pic"])'
```

把 `pic` 下载下来看过才算 `pass`。弹窗内预览只代表当前槽。
补 16:9 的两条路和「重传同一文件按哈希判定未修改」的坑见
[B 站投稿页结构](bilibili/page-anatomy.md)。

### 每个槽位各自验收

1. 打开编辑器，截图读取裁切框和效果预览。
2. 标题主体应位于安全区内，左右留白接近，不能贴边或被头像、按钮、底部信息遮挡。
3. 用户要求居中时，拖动素材后重新截图；以标题组整体视觉中心为准，不只看图片画布中心。
4. 点弹窗内「确认」，并用可见性过滤确认弹窗真的关闭（视频号预渲染了约 35 个隐藏弹窗，读 `innerText` 会拿到无关文案）。
5. 回到主表单读取缩略图，确认对应刚保存的构图。
6. 存在第二个槽时重复一遍。上传专用封面后仍需查看效果预览，不能以文件尺寸正确代替视觉验收。
7. **改完封面要重新点主提交按钮**，关掉封面弹窗不等于提交。

### 每个比例各自出图，不要拿一张图改比例

把 16:9 素材填充到 4:3 会在两侧留下纯色条。观测到的实例：一张命名含 `centered` 的 1440×1080 封面，左边有 80 像素纯黑竖条，文件名的承诺和像素事实相反。

正确做法是对每个目标比例独立做一次「居中裁切再缩放」，宁可裁掉画面边缘，也不要补边：

```python
def cover_crop(source, width, height):
    """按目标比例居中裁切后缩放，绝不填充，因此不会产生黑边。"""
    target = width / height
    sw, sh = source.size
    if sw / sh > target:
        crop_w = round(sh * target)
        left = (sw - crop_w) // 2
        box = (left, 0, left + crop_w, sh)
    else:
        crop_h = round(sw / target)
        top = (sh - crop_h) // 2
        box = (0, top, sw, top + crop_h)
    return source.crop(box).resize((width, height))
```

竖版素材要出 16:9 时裁切会切掉标题，此时改用「原图居中满高 + 自身放大模糊压暗做底」
的合成方式（2026-08-18 给 B 站出 1920×1080 用的就是这套），两侧不是纯色条也不裁字。

上传前扫一遍四边，确认没有近黑条带；文件名、图层名和「我记得是居中的」都不算证据：

```python
px = image.convert("RGB").load()
w, h = image.size
def bar(xs):                      # 从一侧逐列内推，统计近黑列数
    n = 0
    for x in xs:
        col = [px[x, y] for y in range(0, h, max(1, h // 40))]
        if max(max(c) for c in col) > 12:
            break
        n += 1
    return n
assert bar(range(w)) == 0 and bar(range(w - 1, -1, -1)) == 0
```

视频号两张封面的文字排布还要各自适配遮挡：个人主页 `3:4` 卡片底部会被账号名和按钮压住，文字组应上移到上三分之一；聊天分享 `4:3` 卡片没有这层遮挡，可以居中。两张图共用同一套字号和留白比例，避免看起来像两个来源。

## 原创声明（视频号）

原创需要两层状态均通过：

1. 打开「原创权益」弹窗。
2. 勾选「我已阅读并同意《原创声明须知》和《使用条款》」，读取弹窗复选框 `checked=true`。
3. 点击弹窗内「声明原创」。
4. 弹窗关闭后读取创建页主原创复选框 `checked=true`。

只看勾选图标、class 名或点击返回成功都不构成最终证据。

## 单次提交与列表回读

- 点击主提交按钮前再读取一次按钮可用状态和完整字段表。
- 点击一次后记录提交尝试已经发生；按钮加载、跳转、超时或网络抖动时都不重复点击。
- 进入内容列表后重载一次，用账号、文案前缀、提交时间窗口和封面组合指纹定位唯一条目。
- 「处理中」「审核中」「原创审核中」「正在审核」统一报告 `platform_pending`；只有列表明确显示已发布才报告 `published`。

### 重发场景下选对指纹字段

同一素材重发后，列表里会同时存在旧的失败条目和新条目。此时**视频文件名、时长、画面首帧全部相同**，用它们无法区分，按默认优先级去匹配会命中旧条目，把已经失败的状态误报成本次结果。

只用两次之间确实发生变化的字段做指纹：

| 字段 | 重发后是否可用 | 说明 |
| --- | --- | --- |
| 提交时间 | 可用 | 本次提交时间窗内的条目 |
| 标题 / 文案前缀 | 通常可用 | 除非用户要求逐字沿用旧文案 |
| 话题 / 标签组合 | 通常可用 | 新增或调整过时区分度最高 |
| 封面构图 | 重做过封面时可用 | 换过封面才有区分度 |
| 视频文件名 | **不可用** | 同一素材重发时完全相同 |
| 时长 / 首帧 | **不可用** | 同一素材重发时完全相同 |
| 条目 ID / BV 号 | 可用 | 有就优先用它 |

先读取列表中全部候选条目及其状态原文，确认新条目已出现、且能与旧条目逐项区分，再下状态结论。两条都匹配当前指纹时，保留最后确认状态并把候选一并报告，不要猜哪条是自己的。

旧的失败条目是否删除属于用户决定：可以在报告里指出它的存在与状态原文，不要自行删除。

## Review 页面保留

用户要求保留页面时，任务结束后只保留最有价值的 review 页面，通常是唯一匹配条目所在的内容列表。最后在独立命令中执行：

```js
await completeTaskSpace(task.id, { keep: true })
```

只有返回 `{ done: true }` 才能报告页面已保留。**传 id**，传 task 对象会抛
`requires a task space name or id`。
