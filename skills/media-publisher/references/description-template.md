# 视频描述的结构

## 先判定来源，再决定是否生成

本模板只用于**没有用户终稿且平台编辑区为空**的场景。来源优先级固定为：平台页面上的用户
手改文本 → 当前会话逐字文本 → 项目内最近批准稿 → 本模板生成。只要用户已经修改过，模板
即失去写入权；哪怕用户文本不符合下面的结构，也只能指出问题，不能自动覆盖。

恢复或接手发布页时先读描述全文并记录：

```text
description_source: user-edited | user-provided | project-approved | generated
description_text: <逐字全文>
description_length: <实际字符数>
```

`description_source=user-edited` 后将全文冻结。上传封面、选合集、勾原创、改位置或加话题后，
再次逐字回读描述；发现变化立即停下。终稿确认展示页面实际文本，不展示生成草稿，也不拿本地
文案文件反向覆盖页面。

用户明确说“我已经修改并发布”时，这份**实际发布文本**是本期最高优先级的 gold reference：
立即回写项目交接记录，后续平台只继承它的表达核心，不恢复 agent 旧稿。若暂时无法从内容列表
回读平台状态，把“用户报告已发布”与平台验证状态分开记录，不能把用户报告伪装成列表证据。

## 先判断内容形态，不套固定长文

知识技巧短视频（通常约 10 分钟以内）默认使用**钩子型短描述**；长访谈、长教程或资源很多的
内容才使用完整章节与链接骨架。平台字数上限是边界，不是“应该写满”的目标。

| 平台 | 短知识视频默认 | 长内容 / 有批准章节时 |
| --- | --- | --- |
| 微信视频号 | 1–3 行钩子 + 5–10 个精准话题；通常不放 OUTLINE | 只有确实帮助理解时才放 5–8 个大节点 |
| Bilibili | 沿用同一钩子核心；话题放标签字段，不把 `#标签` 堆进简介 | 钩子之后追加全部已核验章节，资源链接按需添加 |

两个平台要适配平台机制，但不要写成两种人格：跨平台继承的是问题张力、核心承诺和关键词，
不是机械复制换行或 `#` 符号。

## 短知识视频：痛点问题 → 能力承诺

第一屏只做两件事：让目标用户认出自己的问题，再让他看到继续观看能获得的能力。解释过程、
系列背景、章节摘要和客套话都不能挤占这两行。

推荐结构：

```text
为什么你的 <对象> 不会 / 不听 / 总失败？
如何让你的 <对象> 获得 <明确能力>？

#领域 #对象 #技术 #产品 #方法
```

2026-08-26 实际发布并由用户确认的样本：

```text
为什么你的 agent 不听 skill 的话？
如何让你的 agent 无所不能？

#AI #Agent #编程 #Skill #Codex #GPT #Codeex #Yoda #prompt #逆向
```

判据：

- 第一行点出观众已经遇到、能立刻自我识别的异常或挫败。
- 第二行承诺本期要解开的能力边界，不提前解释答案；适度保留神秘感是功能，不是缺陷。
- 问句、反差和槽点可以直接使用；不要为了“稳重”改成中性内容摘要。
- 不强制写“本视频是《系列名》第 N 期”、第一人称体验或“希望对大家有帮助”。系列归属由合集、
  封面和账号上下文承担；只有用户明确要求或系列识别本身就是卖点时才写进描述。
- 用户确定的大小写、产品名和术语按原样保留，例如 `agent`、`skill`、`prompt`、`Codeex`。

## 话题 / 标签不是三个保底词

短知识视频默认从内容里提取 **5–10 个互补且精准**的关键词，不要因为完整性门禁只要求 1 个，
就机械停在 `AI / Agent / 编程` 三个泛词。优先覆盖：

1. 领域：`AI`、`编程`；
2. 核心对象或概念：`Agent`、`Skill`、`prompt`、`逆向`；
3. 片中真实出现的模型、工具或产品：`Codex`、`GPT`、`Codeex`、`Yoda`。

不得加入片中未出现的产品、热点词或泛流量词。去重后遵守平台上限：视频号必须由平台生成独立
话题节点；B 站最多 10 个标签，标签写进标签字段，除非用户明确要求，否则不把整串 `#标签`
复制进简介正文。

## 长内容才使用完整骨架

长访谈、长教程或资源密集内容可使用：

```text
钩子（先成立，不依赖后文）

OUTLINE:
00:02:18 章节名
...

LINKS:
...
```

OUTLINE 回答“我能跳到哪”，LINKS 只保留片中真实出现且对观众有用的资源。不要为了模板完整
强行加 `DISCLAIMER`、`CONTACT` 或收尾句。

## 每一条都要有出处

- 时间码必须由脚本从最终成片时间轴生成，不许手写、不许从上一版复制。
- 视频号需要大节点时直接读取成片顶栏进度条的分幕表，不另维护一张会漂移的分组表。
- 导语里的数字、状态、结果承诺必须在片子里真的出现过；描述和封面受同一约束。
- LINKS 里的地址如果来自片中画面，用 OCR 结论，不凭记忆写。
- LINKS 按成片时间排序；把 `MM:SS` 解成秒后比较，不做字符串排序。
- 截断资源或章节时明确写出“这里只列前 N 条”，不做静默截断。

## 用户终稿的跨平台继承

用户在一个平台手改后的终稿是表达策略的最高证据。迁移到另一个平台时：

- 保留前两行的钩子、语气、大小写和核心承诺；不要重新塞回系列介绍或冗长总结。
- 视频号话题节点迁移到 B 站时改为标签字段；不默认把 `#` 串留在 B 站简介里。
- B 站存在最终成片的批准章节时，只在钩子之后追加完整时间轴，不改写钩子。
- 平台拒绝某个标签时只做最小同义替换，并在终稿确认里列出 expected / actual / reason。

## 不要写的东西

- “本视频将带你深入了解”“重新定义效率”等空转开场。
- 把视频内容复述成一段说明书，提前解释掉本该由观看获得的答案。
- 为显得完整而强塞系列名、制作工序、章节数量、客套收尾或第一人称评价。
- 产品意图、内部代号、后续排期承诺，或与本期无关的往期导流清单。

## B 站章节时间轴是完整性要求

只要项目存在最终成片的已核验章节，B 站简介就必须包含全部章节，使用平台可识别并可点击的
逐行时间码：`MM:SS 章节名`，超过一小时改用 `HH:MM:SS`。章节名与时间必须来自最终成片
时间轴；不能用源录屏时间，也不能因为用户手改了导语就把章节漏掉。

若 `description_source=user-edited` 已冻结且缺时间轴，不得用模板重建全文。只有两种合法动作：
用户明确要求后在钩子后做最小追加，或把“缺少章节时间轴”作为终稿门禁失败项交给用户决定。
追加后重新冻结全文、跑 `check_copy.py`，并逐条回读所有时间码与章节名；原终稿确认同时失效。

## 生成稿质量门

只有走到 `description_source=generated` 才检查以下项目；任一失败就保留为本地草稿，不写页面：

- 前两行分别承担“目标用户的真实问题”和“本期提供的能力”，单独截屏仍能成立；
- 没有提前解释答案，仍保留足够的问题张力；
- 没有强制系列介绍、制作视角术语、空转营销句或客套收尾；
- 视频号话题为 5–10 个互补的精准词，且产品/技术都在片中真实出现；
- B 站沿用钩子核心，并在存在已批准章节时追加完整时间轴；
- 没有虚构产品效果、速度、成功率或后续承诺。

用户明确评价生成稿“不行”时，本轮停止自动改写，改用用户页面终稿作为唯一来源，并把失败
归因沉淀进 Skill；不要连续生成多个版本让用户替模型做筛选。
