# 视频描述的结构

## 先判定来源，再决定是否生成

本模板只用于**没有用户终稿且平台编辑区为空**的场景。来源优先级固定为：平台页面上的用户
手改文本 → 当前会话逐字文本 → 项目内最近批准稿 → 本模板生成。只要用户已经修改过，模板
即失去写入权；哪怕用户文本不符合下面的结构，也只能指出问题，不能自动覆盖。

恢复或接手发布页时先读描述全文并记录：

```text
description_source: user-edited | user-provided | project-approved | generated
description_text: <逐字全文>
description_length: <实际字符数>
```

`description_source=user-edited` 后将全文冻结。上传封面、选合集、勾原创、改位置或加话题后，
再次逐字回读描述；发现变化立即停下。终稿确认展示页面实际文本，不展示生成草稿，也不拿本地
文案文件反向覆盖页面。

知识类博主的描述有一个稳定结构，抄它的**骨架**，不抄它的长度。参考样本：张小珺《对游凯超
3 小时访谈》（B 站 BV18Qg96YE1W）。

```
导语（2-4 段，每段一句到三句）
OUTLINE:
00:02:18 章节名
...
LINKS：
DISCLAIMER:
CONTACT:
收尾一句
```

骨架为什么是这个顺序：导语回答「为什么值得点」，OUTLINE 回答「里面有什么、我能跳到哪」，
LINKS 之后都是常驻信息，每期一样，读者会自动略过。把 OUTLINE 放在链接后面等于让想跳章的
人先翻过一堆固定文本。

## 两个平台必须写两版，长度差一个量级

| 平台 | 上限 | 实际该写多长 | OUTLINE |
| --- | --- | --- | --- |
| Bilibili | 简介 ≤ 2000 字 | 用满骨架，导语 3-4 段 | 全部章节 |
| 微信视频号 | 未撞过上限，但信息流里只露前 1-2 行 | 导语压到 2-3 句 | 只留 5-8 个大节点，或整段省掉 |

视频号的描述在信息流里是折叠的，展开率低，所以**第一句必须能独立成立**——它实际承担的是
标题的职责。二十章的 OUTLINE 在手机上是一堵墙，节点超过 8 个就自己合并，合并不了就不放。

## 每一条都要有出处

- **视频号的大节点不要在发布脚本里另立一张分组表。** 顶栏进度条已经有一张分幕表，两边各维护
  一份必然漂移；发布文案直接读那张表。合并规则写死成数据，**不许「取前 N 条」**——取前 N 条
  会把整个后半段丢掉，而那往往才是主体。
- **时间码必须由脚本从成片时间轴生成**，不许手写、不许从上一版复制。改一次片头长度会让
  几十处时间码同时静默失效，而错位的时间码比没有时间码更糟。
- 导语里的数字、状态、结果承诺，必须在片子里真的出现过。描述和封面受同一条约束。
- LINKS 里的地址如果来自片中画面，用 OCR 结论，不凭记忆写。
- **LINKS 要按成片时间排序，不按资源清单的顺序。** 资源清单通常是按重要性编的，直接
  取前 N 条会得到「00:13 / 02:12 / 00:56 / 02:22 / 00:47…」这样的乱序时间码，
  而它紧跟在时间序的 OUTLINE 下面——读者只会以为我们列错了。
  排序要把 `MM:SS` 解成秒再比，**不要拿字符串比**：成片一过 60 分钟，字典序就不再是时间序。
- **截断要说出来。** 只列前 8 条时就写明「这里只列最先出现的 8 条，完整 16 条在片尾」，
  否则读者会把这 8 条当成全部。这条和成片里「不做静默截断」是同一个要求。

## 不要写的东西

- 「本视频将带你深入了解…」这类空转开场：第一句就说事。
- 产品意图、内部代号、后续排期承诺。
- 与本期无关的往期导流长清单（挂合集就够了）。

## 视频号的描述另有五条硬要求

2026-08-18 EP.03 发布时，我给的描述被用户整段重写后才发出去。差异不在信息量，
在**说话的人是谁**。逐条记下判据，下次直接照这个写。

| # | 判据 | 反例（我写的） | 正例（实际发出的） |
| --- | --- | --- | --- |
| 1 | 开头先写「本视频是《系列全称》第 N 期」 | 「配好一个 key，把这个界面从头到尾点一遍」 | 「本视频是《手工川与你一起学 DeepSeek Harness》第三期」 |
| 2 | 博主介绍式，不是操作指令式 | 「配好…点一遍」（在指挥读者） | 「带大家过了一遍」（在介绍自己做了什么） |
| 3 | 不出现制作视角术语 | 「全片 8 幕」「分段」「剪辑清单」 | 直接说内容 |
| 4 | 平铺直叙，不做叙事悬念 | 「从『没配模型』的报错开始，到…」 | 顺序列举讲了哪些东西 |
| 5 | 末尾加一句客套收尾 | 硬停在最后一个章节 | 「希望对大家有所帮助~」 |
| 6 | 开头点名本期具体产出 + 第一人称主观评价 | 「带大家把界面从头到尾过了一遍：配置好…还翻出了…」（中性走查） | 「我让 DeepSeek Harness 做了一个能自定义 system prompt 的插件，很丝滑…体验远超预期，但也有不少坑，非常值得一看~」 |

第 1 条和第 4 条是同一件事的两面：**视频号信息流里描述是折叠的**，只露前一两行，
所以第一句实际承担标题职责。「从报错开始」这种悬念句在展开后才成立，折叠状态下
读者只看到半句没有主语的话，连这是哪个系列都不知道。系列全称放第一句则任何折叠
长度下都成立。系列改名后（如 EP.04「手工川与你一起学 DeepSeek Harness」→
「DeepSeek Harness 实战」），第一句的系列名要跟着换成新名，不要还在用改名前的
旧全称——那不是简称/全称的风格选择，是过时信息。

第 3 条不只是措辞问题：「8 幕」「分段」是**内部工序**，观众买的是内容不是工序，
写出来等于告诉读者「我在按模板生产」。同一条约束也管封面文案。

第 6 条是 2026-08-18 EP.03 定下前 5 条之后，2026-08-19 EP.04 又被重写才补上的：
前 5 条全部满足也不够。「带大家过了一遍」虽然是博主介绍式语气（满足第 2 条），
但内容仍停在「过了一遍什么界面」，没有点名本期具体做出了什么、也没有主观体验
评价。标题承诺什么（如「如何黑掉系统提示词」），第一句就要兑现什么——先说
「我做出了 X」，再补一句「体验怎样、坑在哪」，比中性罗列更接近博主真实的口吻。

B 站不受这五条约束——那边描述完整展开，导语可以做悬念，OUTLINE 也能列全。
**两版分开写，不要把视频号那版加长了当 B 站用，也不要把 B 站那版截短了当视频号用。**

### 草稿质量门

只有走到 `description_source=generated` 才检查以下项目；任一失败就保留为本地草稿，不写页面：

- 第一段能单独说明“这是哪个系列第几期、这期实际做出了什么”；
- 至少一句第一人称判断，且评价能在视频内容中找到依据；
- 没有“本视频将带你”“深入了解”“重新定义效率”等空转句；
- 没有“剪辑、分幕、时间轴、工作文件”等制作视角术语；
- 没有虚构产品效果、速度、成功率或后续承诺；
- 视频号版是 2–3 句可折叠导语，B 站版才使用完整章节与链接骨架。

用户明确评价生成稿“不行”时，本轮停止自动改写，改用用户页面终稿作为唯一来源，并把失败
归因沉淀进 Skill；不要连续生成多个版本让用户替模型做筛选。
