# 竞品调研 Playbook

按模块读取。每个模块给出：要查什么、怎么查、证据怎么定级、报告怎么写。
所有数值进入证据账本后才能写进报告。

## 通用约定

- **口径一致**：两边用同一工具、同一时间点测量。代码行数两边都用 `repo_evidence.py loc`；
  star 等数字写明抓取日期。
- **绝对日期**：所有时间写成 `YYYY-MM-DD` 或 `YYYY-MM`。
- **原始错误保留**：接口失败写进“没能核实的项”，附错误原文的关键部分，例如
  `GET .../stargazers → HTTP 404`。
- **来源分级**：一手资料（代码、提交、官方文档、公告、监管文件）> 可信二手资料（主流媒体、
  数据库）> 自述与营销文案。营销文案只能证明“对方这么说”。
- **隐私**：维护者分析只用公开贡献数据，不输出邮箱，不追查个人身份信息。

## A 差异对比

### 检查清单

| 维度 | 开源对象怎么取 | 产品/公司怎么取 |
| --- | --- | --- |
| 定位与目标用户 | README 首屏、仓库描述、topics | 官网首屏、定价页面向的客户 |
| 实现方式 | 依赖清单、核心模块、是否自己实现关键能力 | 技术博客、招聘 JD、API 文档 |
| 覆盖面 | 支持的平台、渠道、格式清单 | 功能列表、集成市场 |
| 数据与交付 | 输出落地方式（返回、入库、导出） | 部署形态（SaaS、私有化、客户端） |
| 依赖规模 | `loc` 的 `dependency_manifests` | — |
| 代码规模 | `loc` 的 `source_lines`、`test_lines` | — |
| 协议/条款 | `facts.license`，`NOASSERTION` 时读 LICENSE 原文 | 服务条款、可商用范围 |
| 时间线 | `facts.created_at`、`history.root_commits` | 成立、发布、融资时间 |
| 商业化 | 赞助、付费版、托管服务 | 定价、收入披露 |

### 写法

- 一张对比表，行是维度，列是对象；表下补充两边唯一的交集或冲突点，例如“两边只有两个平台
  重叠，而且实现路线完全不同”。
- 观察到对象正朝同一方向演进时单独写出（例如一方的新版本开始宣传对方的核心能力），
  并说明这是趋同，不是派生。

## B 血缘溯源

### 四类证据

1. **平台关系**：`facts.fork`、`parent`、`source`。`fork: false` 只说明不是用平台 fork 按钮建的，
   不排除拷贝后另建仓库。
2. **起源提交**：`history.root_commits` 的提交说明、`message_signals` 里的 forked、
   ported from、based on、zero copied、from scratch 等；重写提交要看它删了什么。
3. **相同文件**：`lineage` 的 `shared_blobs`。blob 哈希相同就是逐字节相同的文件；
   改名后仍相同也能抓到。早期 fork 必须加 `--source-all-history`。
4. **特有标识符与名称**：`lineage` 的 `identifier_commits`（源项目特有的类名、函数名，
   区分大小写）与 `mention_commits`（源项目名、作者名，不区分大小写）。补充手工挑选的
   标识符：签名函数、客户端类、内部协议常量最有区分度。

### 证据等级与结论

| 等级 | 条件 | 可写的结论 |
| --- | --- | --- |
| 强 | 平台 fork 关系；或共享 blob ≥ 1 个非模板文件；或起源提交自述来源 | 派生（说明派生自哪个版本、后来是否重写） |
| 中 | 多个特有标识符命中，但无共享 blob | 部分借鉴或改写，附命中列表 |
| 弱 | 只有名称提及（可能是致谢或对比） | 有关联提及，不构成派生 |
| 无 | 四类全部为零，且做过反向对照 | 独立实现，没有代码复用证据 |

- **反向对照**：同一次调研里，至少对一个已知有关系的源跑一次 `lineage`（例如起源提交
  点名的项目），确认检测方法在这个仓库上有效；结果为零时，“无关系”的结论才可靠。
- 名称提及要读上下文：致谢、对比表、迁移指南都会提到别的项目。
- 通用标识符（`get_config`、`BaseClient`）撞车不算证据，只计特有标识符。
- 写清检索范围：提交总数、检索了哪些词、比对了多少个文件。

## C 含金量

### 1. 能力来源图

- 列出每个功能由谁实现：自研模块，还是上游工具或库（给出上游名称、star、创建时间、
  协议）。
- 找出“最难的部分”在谁手里：反爬签名、模型、数据、实时性、合规资质等。
- 自研部分用 `loc.by_directory` 给出代码占比，并读最大的几个文件确认内容。

### 2. 工程质量

- 测试：`test_functions`、`test_to_source`；查是否有 lint、类型检查、CI。
- 发布节奏：CHANGELOG、tag、版本号。
- 读两三个核心文件：错误处理、可扩展点、版本锁定这类工程细节。

### 3. 热度成色（启发式，不是定论）

| 指标 | 来源 | 读法 |
| --- | --- | --- |
| 每月新增 star | `derived.stars_per_month` | 和同类对比，异常陡峭时提示核查 |
| fork/star | `derived.fork_to_star_pct` | 偏低说明收藏多、动手改的少 |
| 每千 star 的 issue 数 | `derived.issues_per_1k_stars` | 偏低说明真实使用反馈少 |
| PR 合并率 | `derived.merged_pr_share` | 外部贡献被接纳的程度 |
| star 抽样 | `facts --star-sample` | 低信号账号占比；接口不可用时写“无法核实” |
| 安装量 | PyPI/npm/应用商店 | 先确认包的归属 |

- 和对手并排列出，比较相对高低，不给绝对阈值。
- 不能断言“刷星”，除非抽样中出现明显集中的低信号账号，并且写明样本量与定义。
- 可附营销投入的证据，例如提交历史里有大量文案与传播相关的提交，用来解释热度来源，不作道德判断。

### 4. 可持续性

- 维护集中度：`history.top1_author_share`，先用 `--alias` 合并同一人的身份。
- 停更期：`history.quiet_months`。
- 上游依赖风险：关键上游的维护活跃度、协议、是否单点。
- 协议对使用者的影响：能否商用、是否传染。

### 5. 结论写法

- 一句话结论：“含金量主要在 X，不在 Y”。
- 分别说清“值得用于什么”和“不适合什么”，以及“值得借鉴哪部分代码”。

## D 投资视角

### 开头必写

> 我不是持牌投资顾问，以下是业务和技术尽调层面的分析，不构成投资建议。

### 检查顺序

1. **代币与骗局**：README 或官网是否声明“无官方代币”；搜索同名代币，提示风险。
2. **实体与收入**：公司注册、融资公告、付费版、托管服务、赞助收入。查不到就写“未查到”，
   不推测。
3. **护城河**：协议是否允许任意 fork、关键能力是否在上游、平台方是否在做内置替代。
4. **价值链位置**：同赛道拿到融资的公司及其轮次、金额、估值，每个数字附来源；
   来源说法不一时并列写出。
5. **合规风险**：服务条款冲突、数据抓取的法律风险，并说明商业化后风险如何转移。
6. **关键人风险**：维护集中度、停更史。
7. **热度成色**：引用 C 模块的结论，不重复计算。

### 结论写法

- 先回答“按公司来投有没有价值”，再列 2–3 条“可能成立的投资逻辑”（投人、转型、
  被收购等），每条写清它的前提和会撞上的对手。
- 列出“需要向创始人要的数据”：创业意愿、团队、真实活跃用户、收入、法律意见。
- 不给买入、卖出、仓位、估值目标或收益预期。

## 报告骨架

```markdown
**一句话结论。**（直接回答用户的问题）

## <模块标题>
- 证据 1（来源）
- 证据 2（来源）

| 维度 | 对象 A | 对象 B |
| --- | --- | --- |

## 没能核实的项
- <项>：<原因与原始错误>

Sources:
- 来源标题：链接地址
```

追问时只写新增模块，引用前文结论而不是整段重复。
