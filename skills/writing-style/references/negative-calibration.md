# 用户负向校准：2026-09-08

来源：用户对 Copilot 文章的直接反馈。它不增加历史语料篇数，不代表所有真人的写法。
用户明确排斥的是以下表达在文章中承担的作用，优先于旧画像的高频修辞和固定结构。

| 用户指出的原句／句式 | 被排斥的写作动作 | 本文中的编辑处理 |
|---|---|---|
| 账号模型和客户端是三件事 | 为分类而分类，先搭讲义框架 | 在用到权限时写 Copilot 可选 Claude 不等于 Claude 订阅 |
| 先把什么说准确一点 | 宣布纠正读者，再说事实 | 直接写权限、接口或版本事实 |
| 这次要做的 | 以写作任务代替实际内容 | 写已经完成的操作与结果；没有新增信息就删 |
| 什么什么负责另一段 | 用分工旁白把框架串起来 | 写 CC-Switch 中实际选择和配置的项 |
| 这是什么什么需要说清楚的地方的部分 | 解释为何设置这一节 | 删掉，让该节直接从事实开始 |
| 网关路由和账号会受什么影响？ | 用过大的泛问句做标题 | 在相关段落直接写上游地址、用量和限制 |
| 账号风险不能写成零 | 把给作者的审稿要求塞进正文 | 写逆向接口、限流、可验证的未知范围 |
| 数据经过的环节变多也值得留意 | 提醒读者重视，却没提供信息 | 写哪些程序接触请求、可能保存什么 |
| 解决的是一个很具体的问题 | 用抽象总结再包装一次已有结论 | 删掉重复结尾，保留项目和安装入口 |

这些是反例，不是替换字典。把“先说清楚”换成“有必要厘清”，把“值得留意”换成
“不容忽视”，把“具体问题”换成“真实痛点”，仍然应返修。上表右列仅适用于本次
材料，禁止作为后续文章的固定句模。

## 写作前

从用户材料中列出可写的操作、结果、判断与未知项。让它们决定顺序，不为文章补齐
“定义—区分—方案—边界—总结”。如果用户明确提出一个问题，可以原样进入文章；
不要自行添加一串泛问句模拟对话。

## 逐段审读

先遮住正文只读标题：能否知道这里实际讲什么？然后回读每段，指出新增的事实、
操作、因果、判断或必要衔接。删掉一句后若信息与语气都没有损失，优先删掉。

凡是指导读者“怎么理解这篇文章”、指导作者“应该怎么写风险”、替章节预告任务、
替结尾再包装意义的句子，都要审查。保留时必须说明它解决了哪处具体歧义。
不要把“账号”“入口”“环节”“链路”“边界”等词一律禁用：有可指认对象时可以用。

操作步骤、真实比较、必要限制、引用与品牌原文可以保留。不要为逃过检查删去事实
限定、改造引语，或编造吐槽、凌晨调试、失败经历和个人情绪。自然也不等于全篇短句。

不再复制一份反 AI 规则或脚本。交付前必须完成该依赖的篇章审读，不能拿指标通过代替。
