# 蒸馏透镜

先理解一次经验中真正有效的部分，再决定它是否值得成为 Skill。

## 五个问题

1. **结果是什么？** 用用户能判断的结果表达，不写内部工具动作。
2. **为什么有效？** 抽出稳定判断、顺序和约束，不复述全部调试过程。
3. **哪些会变？** 渠道、模型、路径、品牌、项目名通常应配置化，而不是拆成多个 Skill。
4. **哪里会失败？** 记录失败信号、恢复路径和最终验收，避免将“编译成功”误认为交付成功。
5. **什么必须留在边界内？** 私人背景、客户数据、密钥、专有规则与作者环境不得进入可分发内容。

## 提升检查

一项经验适合提升为 Skill，通常同时满足：

- 有一次真实验证，且可以描述下一次如何验收；
- 用户结果在另一个项目或用户身上仍有意义；
- 触发边界清楚，至少能写出一个不触发场景；
- 核心流程能独立于原项目运行，或能明确标出所需配置；
- 与现有 Skill 的差异是结果或核心判断，而不只是换了工具。

## 反模式

- 将每个 bug、文件名或项目名称直接命名为 Skill；
- 把聊天中提供的背景信息泄漏到公开名称、描述或示例；
- 只写“自动化”，没有输入、输出和验收；
- 因为技术实现复杂就拆成 Skill Kit，而每个阶段并没有独立用户价值；
- 因为一次成功就忽略失败恢复与边界。
