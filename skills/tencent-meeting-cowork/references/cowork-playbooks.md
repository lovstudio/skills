# 协作模式做法

四种模式共用同一份 `notes.md`。先读完整份，再按下面的做法交付。所有对外文字都只交给用户，
由用户自己决定发不发。

## 共同的证据台账

起草任何简报、消息或成果之前，先分清每句话的来源：

| 类别 | 内容 | 怎么用 |
| --- | --- | --- |
| 转述 | 带 s / c / n 编号的内容 | 可以写“纪要记录为…”；对外使用前核对专名和数字 |
| 待办 | 带 t 编号、标了负责人的事项 | 负责人以纪要标注为准；没标的列为“未指定” |
| 解读 | 实时笔记里的「解读」 | 只帮助理解语境；不当事实，不进对外文字 |
| 用户确认 | 用户在本次对话里说的事实、决定、底线 | 可以直接写进成果 |
| 本人材料 | 用户指给你的文件、往期资料、报价单 | 成果的实质内容从这里来 |
| Profile | `followup_style`、`counterpart_notes` 等长期记录 | 语气、称呼、渠道 |
| 推断 | 从上下文推出、但没人说过的 | 只用来决定先问什么、先做什么 |
| 看不到 | 逐字稿、屏幕共享、会议聊天、会后的私下沟通、会议日期 | 影响结论时明确告诉用户 |

规则：

- 推断和解读都不能写进对外文字当成事实。
- 关于用户本人的能力、经历、价格、时间、承诺，只能来自经用户核对的转述、用户确认、本人材料
  或 Profile；其余写成【待确认：…】。
- 关于对方的立场和要求，沿用纪要的力度：“询问”不写成“要求”，“建议”不写成“条件”，
  “表示会考虑”不写成“同意”。

## 三处对齐（每种模式都先做）

1. 列出纪要待办（t）。
2. 逐条读实时笔记，找四类没进待办清单的内容，记下编号：
   - 别人向我提的要求或问题：要我补什么、明确什么、提供什么；
   - 我说过会做的事：表示、承诺、计划、答应；
   - 别人答应的事：对我有用、需要我跟进的；
   - 没解决的异议、条件和顾虑：对方不能接受什么、还在评估什么。
3. 看每一条在后面的笔记里有没有被回应。被追问后当场答复了的，写成“已在会上回应（n12.2）”，
   不再列为待办；只回应了一半的，写清还差什么。
4. 核对数字与专名：
   - “核对线索”里只在实时笔记出现的数字，逐个判断是否与待办或成果有关；
   - 同一项数据在摘要、卡片、实时笔记里说法不同的，并列写出各自的编号；
   - 同一个人或机构有几种写法的，列出来问用户哪个对。

## brief：会后行动简报

只给链接、没说要什么时的默认模式。结构：

1. **一句话结论**：这场会到了哪一步，下一步卡在谁手里。
2. **我的事**：纪要待办里属于我的，加上三处对齐找到的（注明“未进待办清单”）。每条写：做什么、
   给谁、对方拿它做什么（评估、决策、存档）、会上已定的相关条件、期限（会上没说就写【待确认】）、编号。
3. **对方的事**：需要我跟进或等待的。
4. **悬而未决**：异议、条件、没答完的问题，每条一句建议怎么接。
5. **待核对**：专名与数字。
6. **覆盖范围**：来源、“我”的认定依据、看不到的部分。
7. 给一个建议的下一步，并问用户先做哪件，例如“先把 t2 的材料骨架搭出来，还是先起草跟进消息？”

保持短。用户要的是“我该做什么”，不是把纪要再复述一遍。

## catch-up：这场会讲了什么

1. 一句话：会议目的与结果。
2. **定下来的**：双方确认过的结论，带编号；数字用核对过的。
3. **没定的**：分歧、待评估的条件、留到会后的问题。
4. **与我有关的**：知道“我”是谁时单列；用户没参会时，标出哪些需要他表态。
5. 摘要没写、但实时笔记里有的要点单独提一句：这是这份简报相对页面摘要多出来的信息。

不照抄摘要。页面上已经有摘要，这里的价值在于对齐后的差异和取舍。

## work：把答应的活做出来

1. **列需求单**：谁要、要什么、用来做什么、期限、会上已谈定的条件，以及对方表达过的顾虑
   （成果需要回应的点）。每条带编号。
2. **找材料**：纪要只能告诉你“要交什么、对方在意什么”。成果的实质内容（课程内容、数据、案例、
   报价明细）必须来自用户的材料或确认。先问用户材料在哪；有就读，没有就搭骨架，把每个空位
   标成【待确认】。不要把纪要里的只言片语扩写成细节。
3. **交付成果**：按对方的评估视角组织，对方在会上问过的问题就是目录的线索；对方明确在意的点
   逐条回应到位；数字用核对过的。能先做的先做，不因为有待确认项就停下全部工作。
4. 需要长文写作、排版或格式转换时，可交给对应 Skill，并把需求单与依据一起交过去。
5. **附跟进消息**：用 follow-up 的做法起草一条随成果发出的消息。
6. **记录未覆盖**：屏幕共享、聊天、会后沟通可能改变需求时，单独列出。

## follow-up：会后跟进消息

1. **定目标**：对齐共识、交付材料、推动对方的待办、约下一次。一条消息只有一个主目标；目标
   不清楚时问用户一个问题。
2. **收件人与渠道**：发给会上的对接人，不是所有参会者。渠道来自请求或 `followup_channel`；
   都没有时给一版即时通讯短消息，并说明可以改成邮件。
3. **内容顺序**：承接一句 → 我方理解的共识（只写双方在会上确认过的，2–4 条）→ 我方接下来做
   什么、什么时候（没依据写【待确认】）→ 需要对方做什么 → 附件说明。
4. **写法**：
   - 即时通讯：短句，按发送顺序分成几条，不用标题和 Markdown 符号；
   - 邮件：一行标题加正文，条目可以编号；
   - 语气按 `followup_style` 与 `counterpart_notes`；没有时用克制的商务口吻，不套近乎，不夸大。
5. **禁区**：不写「解读」；不把对方的“询问”“建议”写成“已同意”；不替对方概括其内部流程；
   不写用户没确认的时间和价格；专名先核对。
6. **自检**：逐句问依据是什么（编号或用户确认）；有没有新增承诺；对方读到会不会觉得被
   “记录在案”地施压。
7. **交付格式**：

   ```text
   要完成的事：交付大纲并对齐评估口径（回应 t2、n13.2）
   推荐（分 3 条发）：
   ```

   代码块里放可以直接复制的原文；块外写依据编号、待确认项和“未发送”。

## 常见情形

| 情形 | 做法 |
| --- | --- |
| 链接要登录或已失效 | 说明读不到；请用户在已登录的浏览器里把页面另存为 HTML（用 `--html`）、重新生成链接，或粘贴纪要文本。不索取账号、Cookie、验证码 |
| 只有粘贴的纪要文本 | 不跑脚本，按同样规则工作；用原句代替编号；文本里没有实时笔记时说明无法核对摘要的漏项 |
| 不知道“我”是谁（`self` 为 null） | 列出发言人问一次；用户没参会时按旁观者交付 catch-up，待办不标“我的” |
| 名字是部分匹配的（`match: partial`） | 交付第一行请用户确认“把你认作 X 对吗” |
| 纪要没有列待办 | 全部从实时笔记里找，并说明“纪要未列待办，以下由实时笔记整理” |
| 只有摘要、没有实时笔记 | 说明无法核对摘要的漏项；结论与数字都按“摘要记录为”表述 |
| 摘要与实时笔记的数字冲突 | 并列写出两处的编号与说法，标【待核对】；成果里用用户确认后的数 |
| 同一名字有几种写法 | 列出各写法与编号问用户；确认之前，对外文字里写【待核对：名称】 |
| 对方提了没解决的顾虑 | 在简报的“悬而未决”里单列，并在 work 的成果里正面回应 |
| 关键人物不在发言人列表里 | 按转述里的称呼提到他，并提醒用户：这位可能是决策人，跟进时要不要一并知会 |
| 涉及钱（报价、分成、退款） | 只复述纪要的记录与用户的确认，不建议接受或拒绝；把需要用户决定的点列出来 |
| 用户要“直接帮我发” | 说明本 Skill 不发送；可以放进剪贴板，由用户粘贴发送 |
| 用户想把待办放进任务工具 | 给出可以复制的清单；写入任务系统交给对应 Skill，并由用户确认后再写 |
| 想对一下微信里的语气，或确认是否已经发过 | 可选交给 `lov-wdb-cowork` 读对应会话 |
| 会议很长（实时笔记几十条） | 先只抓三处对齐的四类内容，再按需展开；不逐条复述 |
